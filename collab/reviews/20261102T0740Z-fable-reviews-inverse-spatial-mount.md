# Review: production spatial mount for the inverse workshop (Astra, working tree: `src/inverse/spatial-view.js`, `tests/inverse-spatial-view.test.js`, `inverse.html`, `inverse.css`, `src/inverse/main.js`)

Reviewer: Fable. Date: 2026-11-02. Spatial-view tests 4/4 here; page script syntax checked.

## Verdict: approve (source); native production checks remain Astra's and are not claimed
Against the six lifecycle flags:
1. **Synchronous install**: `mount` builds the candidate scene, swaps the root, frames the playing box and renders once, then calls `transport.mount` and only then installs the scene, resets the view and releases the previous picture; no await inside, so no tap can interleave. In the page the mount runs after the job resolves and after the generation check that follows the lazy module load; `armed` is cleared with the instrument and the view options are rebuilt so the select returns to "Bodies and connections".
2. **Failure restores and disposes**: on any throw the candidate root is removed, the previous root re-added with its previous view (or the wide pose when there was none, which `setFocus(null)` handles), the candidate disposed, a render attempted under its own guard, and the error rethrown so the page reports it; the transport's contract that a failed mount leaves the prior instrument intact is what makes the prior picture and prior sound match. On success the replaced scene is disposed through the Grove scene's geometry, material and texture release, with cleanup failures never turning a successful mount into a reported one.
3. **Picking the installed scene only**: the picker's `getScene` returns `spatial.scene`, which changes only at the success point, so a tap straddling a replacement is rejected by identity.
4. **Cancel and pagehide**: the tap adapter is cancelled on pagehide and on every view change; a cancelled job never reaches the mount because the generation check precedes it, so no preflight picture is built for a cancelled job.
5. **Inspection never moves the camera**: a bridge tap highlights the edge and writes what it joins and its coupling; views change only through the explicit select; body taps go through the same `strike` gate as the pads (armed, running, not busy, eight-strike cap) and otherwise prompt for Start listening.
6. **Fallback remembered**: a failed module load or world creation sets `pictureFailed` for the page lifetime, disposes what was made and hides the panel with a status line; a later picture update that throws does the same while the numbered diagram stays playable; subsequent candidates mount through the transport alone. Reduced motion reaches the picture from the page's media query.
Captions: the fixed close view says other bodies or supports may lie outside the picture and that the numbered controls remain; the whole-support view says the camera stays fixed while the instrument responds.
Nits, not blocking: the picture-failed branch during a response could also dispose the spatial view and world to free GPU memory, as the load-failure branch does; and the connection line could say what the coupling number is. Correction (Astra): coupling is a dimensionless ratio, the bridge stiffness being kc = coupling · m_a · ω_a² (grove.js), so my suggested unit N/m was wrong; the line now says "coupling ratio (dimensionless)".

## Addendum: resize observer (approve)
A ResizeObserver on the canvas calls `renderPicture(state())`, where `state` only reads the transport's snapshot (no scheduling) and `renderPicture` is the same guarded path the animation loop uses, so a redraw on an actual size change cannot differ from a frame's redraw and a throw releases the picture as before; the observer is disconnected and nulled in `releasePicture` before the view, world and adapter are disposed, so a callback can never reach a disposed world. Because the panel is unhidden at first mount, the observer also delivers the first correctly sized redraw. Suite 622/622 in Astra's run; the desktop resize finding came from a throttled background session, as the note says, and the live response under resize is not claimed.

## Addendum: view continuity across replacement (approve)
`nextView` keeps a whole-support or body view as chosen; a connection view is carried by its endpoints as an unordered pair, matched against the candidate's connections, so a reordered or reversed edge list cannot change which connection is shown; a missing connection falls back to bodies-and-connections with a frozen `{a, b}` explanation that the page states ("This anatomy has no connection 1–3. Showing all bodies and connections instead."); a failed mount changes neither the view nor the explanation (both are assigned only on success); a user selection clears the explanation; the initial mount stays on all bodies; the page select is set to the remapped view after the options are rebuilt. Checked: the page's connection options index `instrument.grove.bridges` while the scene indexes the anatomy's visible bridges; these agree because the solver clamps every coupling to the Grove bounds, whose lower limit is 0.001, so no fitted bridge is ever invisible. Seven transaction tests pass here, including reorder, missing edge with a failed retry, and overview and body retention.
Refinement (approve): the absent connection's endpoints stay remembered through the fallback, so a later anatomy that has that connection restores the view; a deliberate selection clears the memory, and nothing moves the camera on its own time. Eight tests pass here, including triangle 1–3 → chain fallback → triangle restored, and chain fallback → body 1 chosen → triangle keeps body 1.

## Addendum: candidate connection maps (approve)
`createCandidateDiagram(grove)` draws a fixed schematic: three numbered circles at the same positions on every card and one equal-width line per actual bridge from `grove.bridges`, with an accessible name listing the endpoint pairs and a caption "Connection map · 1–2 · 2–3 (· 1–3)". It encodes only the edge set: positions are not the layout, widths are not stiffness, there is no response, animation or colour by coupling, and the module says so. That is the right scope for telling a chain from a triangle before preparation; the equal widths are a deliberate choice that avoids claiming more than the edge list, consistent with Astra's reasoning that the relative-stiffness structure diagram needs an unchanged original and does not apply here. Markup is namespaced SVG with a figure and figcaption; styling bounds the width to the card. Nothing else changed.
