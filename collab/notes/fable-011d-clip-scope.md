# 011d scope: bounded MIDI Clip import into the reviewed expression evaluator (Fable, 2026-11-02; scope and sources only, no parser code)

The text carries, as text and not only as figures: Appendix F Table 30, the 8-byte packet layouts of every Message Type 0x4 channel-voice message (Note Off and On with attribute type and data, Poly Pressure, Registered and Assignable Per-Note Controllers with index, Per-Note Management with option flags, Control Change, RPN and NRPN with bank and index, relative controllers, Per-Note Pitch Bend, Pitch Bend, Program Change, Channel Pressure); section 7.2.3 (Delta Clockstamp: DCTPQ 1 to 65,535 with 0 reserved, DC ticks since the last event, the NOOP restart rule after 1,048,575 ticks, simultaneous events sharing a clockstamp and stored in presentation order); the Start of Clip and End of Clip rules (first and last events of the Clip Sequence Data, Start of Clip preceded by a Delta Clockstamp). Fetching it is a download; Astra obtained the UMP PDF in its own environment and can do the same, or Michael can place it under an untracked `reference/`. No container code before it is read.

## Scope constraints (first slice)
1. **Input bound**: a Clip file of at most 256 KiB (the SMF reader's bound), read once, with the Clip Sequence Data decoded as a sequence of 32-bit big-endian UMP words; message length from the message type nibble as the UMP text defines it; a truncated packet is a refusal, not a guess.
2. **Message routing**: Message Type 0x4 messages in the evaluator's subset become ExpressionScore events with raw integers preserved (velocity16, attribute type and data16, index8, bank8, data32, flags), `group` and `channel` from the packet; the other 0x4 messages (Program Change, Channel Pressure, Assignable, RPN and NRPN other than #00/00 and #00/07, relative controllers) are kept as the evaluator's reported *unsupported* and *partial* kinds, never silently dropped; Delta Clockstamp and DCTPQ set time; NOOP, JR Clock and JR Timestamp are counted and ignored (the text says most receivers ignore them in a file); Start of Clip and End of Clip are required at the two ends and nothing is accepted after End of Clip; every other message type is counted by type as unsupported.
3. **Time**: seconds = cumulative DC ticks ÷ DCTPQ × 60 ÷ tempo, with tempo from the Clip's own tempo message where the Clip specification places it; if the file declares none, the reader uses 120 BPM and reports it as assumed; the ExpressionScore's `time` is seconds, non-decreasing, with `order` from presentation order as the text requires.
4. **Bounds into the evaluator**: `source.kind: 'clip'`, `source.name` the file name bounded to 120 characters; `bounds.maxVoices` and `maxEvents` from the count of Note Ons and events found, capped at the evaluator's limits (1,024 and 65,536) with refusal beyond; `mapping` the bellows mapping version 1 with the neutral values the fixtures use; then `validateExpressionScore` is the only gate, and the adapter's own study limits (8 voices, 512 events, 30 s, 40 s) apply at render time, reported as the page already reports them.
5. **No invented semantics**: nothing in the reader interprets a message the evaluator does not already interpret; no live transport, no device support, no Safari MIDI 2.0 claim.

## The minimal known file, and a round trip
A `encodeClipSequence(score)` in my ownership that encodes an ExpressionScore's events as UMP packets with Delta Clockstamps from Table 30 and section 7.2.3, citing the section for each field, gives the parser a known input before any real file exists: the four-voice fixture and the musical study encoded, decoded, and required to equal their canonical ExpressionScore byte for byte, and the decoded score rendered through the already-reviewed compiled evaluator to equal the fixture's evaluation at every sampled time. The container wrapper waits for M2-116-U; until then the Clip Sequence Data decoder is testable on its own. A real file from another application, when one is available, is the validation that matters and is reported as such.
