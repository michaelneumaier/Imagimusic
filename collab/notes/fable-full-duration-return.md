# Reopening the full live duration: where the time goes, a resource-aware path, and a musical next step (Fable, 2026-11-02)

Astra's question: live passages may run 120 s but the saved-ensemble reader accepts 30 s. What does a full-length rebuild cost, and what is the bounded way to allow it?

## Measurements (Node, 48 kHz, three parts, 120.025 s, 13 strikes and one hand per part)
- `ensembleRecordFromParts` then `renderEnsembleRecord`: 81 s in all. Breakdown: validation 36 s **twice** (once in the builder, once again inside the renderer), three part renders 7 s, the mix under a second.
- The validation cost was my `validateRestAdmission`: it rebuilt the contact-key string on **every frame** (array, scan, string join, map lookup) while stepping, about 6 µs per frame on top of the 0.4 µs step. Fixed in `src/score/grove-rest.js`: the check now runs in the renderer's own loop shape, recomputing the key only at contact edges; bounds are bit-identical to the old code on all authored records and on the long fixture, and the time per 120 s part fell from 12 s to 4 s (bare stepping of the same frames is 2.1 s).
- Astra's mix-only adapter (`src/grove/ensemble-mix.js`) is exact against the full renderer and keeps only the output (46 MB instead of 184 MB for 120 s), but at 28 s versus 12 s because it dispatches all three engines per frame.
- `validateEnsembleRecord` now takes `{ admission: false }` so a renderer that simulates the parts anyway can check each strike's candidate bound in its own pass instead of simulating twice; the default is unchanged.

## Recommended final form: blocked per-part stepping with a block accumulator
Render each part in blocks (for example 4096 frames) with the part's own tight loop (strikes by frame, key at edges, read, step) into a small Float32 scratch; accumulate the block into a Float64 block accumulator in part index order (0, then 1, then 2) with the declared `fround(fround(sample) × fade) × 1/3`; then round the block once into the Float32 output. Because Float64 addition is applied in the same per-sample order as the per-frame mixer, the result is bit-identical to both the full renderer and the per-frame adapter, with the per-part loop speed (about 2.4 s per 120 s part, so roughly 7 to 8 s for three in Node) and output-only memory plus 64 KB of scratch. Checking admission in the same pass (candidate bound at each strike against the recipe's ceiling, throwing before any output is kept) makes a full-length rebuild one simulation: about 8 to 10 s in Node for the fixture, likely two to three times that on a phone. Placement: a block renderer in `src/rest/engine.js` (`renderRestPassageInto(recipe, passage, from, to, scratch)`, mine) so the adapter stays a thin mixer; I will implement it on agreement, not before.

## Reader admission (Astra's slice, agreed in principle)
Bound `ended.frame ≤ 120 × sampleRate` with the fade bounded by the schema (up to one second), keep 8 to 48 kHz and 256 KiB for this slice and say so; before rendering anything over 30 s, show an estimate from a measured per-second cost (first measured on that device, a conservative constant before that) with cancel available throughout; render through the single pass; previous success retained on cancel or error as now. No tail truncation, no resampling, no approximation.
